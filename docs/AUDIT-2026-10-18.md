## 1. 总体评价

这是一个**方法论意识明显高于同类工作**的研究仓库。研究问题（"错误答案首先发生在生命周期哪个边界"）提得干净，oracle 三条件控制设计正确，研究日志表现出罕见的自我纠错纪律（三次无效的 LoCoMo n=50 运行被明确保留为阴性结果、拒绝解释 "Real > Oracle" 倒挂、预注册 gate 后才扩样本）。E0 证据充分性 gate 用**基准参考答案**而非模型预测做判据，是正确的非循环设计。

但核心归因仪器（failure attribution）存在**协议分裂**：README 和校准脚本实现的是"语义错误才判 F6"，而主实验 runner 实际仍用词法评分判 F6——这正是他们自己校准阶段识别并修复的假阳性通路。此外证据匹配、演化阶段测量、judge 可靠性、配对统计方面有六个会影响论文主结论的问题。**建议先在 n=50 之前修复 Critical 级问题，再冻结协议扩样本。**

## 2. 优点（应保持）

1. **Oracle 控制设计正确**：Real / Oracle Memory / Oracle Context 三条件把"记忆侧证据丢失"与"下游推理失败"分离，README 明确 oracle 是 control 而非竞争系统。
2. **研究日志纪律**：无效运行保留为阴性记录；"协议不在检查 50 样本结果后更改，除非预注册的 bug"；倒挂现象拒绝解释。
3. **E0 gate 的非循环设计**（`experiments/run_oracle_experiments.py:208-246`）：用基准参考答案做充分性判据，docstring 明确说明"用模型的失败答案会使 E0 依赖于被诊断的失败本身"。
4. **校准闭环**：发现词法假阴性（Glass Menagerie F1=0.36）、judge 假阴性、证据/问题错配三类 artifact 后，新增 E0 / EVAL 类别而不是硬判 F6。
5. **Provenance 优先匹配**（`tracing/lifecycle.py:81-88`）：turn_id 优先于 session 身份，避免同句重复文本错配。
6. **F6 仅作 candidate 归因**，且要求证据充分 + 全链路到达 + 非低置信度。
7. **后验工具链**（`analyze_oracle_results.py` / `semantic_calibration.py` / `diagnose_formation.py`）都不重复调用 LLM，bootstrap CI 已实现（`analyze_oracle_results.py:48-64`）。
8. 适配器显式标记 `granularity: unresolved` 的证据，未静默吞掉。

## 3. Critical 级问题（威胁主结论有效性）

### C1. 主实验 runner 的 F6 判定仍走词法评分——与 README 协议不一致

- **位置**：`experiments/run_oracle_experiments.py:249-267`（`_answer_failure_type`）、`tracing/failure_attribution.py:86-117`（`attribute_failure`）对比 `experiments/semantic_calibration.py:127-152`。
- **观察**：`summary.json` 的 `first_answer_failure_distribution`（每次全量跑的主要定量输出）中，F6 的门槛是 `answer.correct is False`，即词法评分（EM 或 token-F1≥0.5 或时间/短语规则）。而 README（91-95 行）和校准脚本实现的是"语义错误 + 非低置信度 → F6_REASONING_CANDIDATE"。
- **后果**：校准阶段亲手修掉的假阳性通路（如 58bf7951 "The Glass Menagerie" F1=0.36 → 词法错误 → F6 candidate）会在 n=50 全量跑中**原样复现**，且必须再跑一次 semantic_calibration 才能得到论文数字。更糟的是文档声称的协议与代码实现的协议不是同一个。
- **建议**：把 `_answer_failure_type` 改为消费 `answer.semantic_correct`（校准层已写好逻辑），或让 runner 在生成答案后直接调用统一归因函数；至少让 summary 同时报告词法归因和语义归因两列并说明差异。

### C2. 归因规则有三份实现，其中一份是循环设计

- **位置**：`tracing/failure_attribution.py::_ensure_evidence_sufficiency`（用**模型失败答案**做 judge candidate，43-56 行）vs `run_oracle_experiments.py::_evidence_sufficiency`（用基准答案，正确）vs `semantic_calibration.py` 内联逻辑。
- **观察**：E0 gate 文档（`docs/research/2026-10-09-e0-gate-experiment-integration.md`）明确否决了前者，但只要调用方没有预计算 gate（`attribute_failure` 的 `existing` 分支），循环版本就会生效——`tests/test_failure_attribution.py` 正是直接调它。另注意 `_answer_failure_type:256` 的 `if sufficiency and ...`：gate 为空 dict 时**直接绕过 gate** 进入 F1-F6。
- **后果**：同一份 comparison.jsonl 经三条路径会得到不同标签；类别名也已漂移（`E0_EVIDENCE_INSUFFICIENCY` vs `E0_EVIDENCE_INSUFFICIENT`，`EVAL_EVIDENCE_SUFFICIENCY` vs `EVAL_SEMANTIC_UNCERTAIN`，`F6_REASONING` vs `F6_REASONING_CANDIDATE`）。
- **建议**：收敛为一个 `attribution.py` 模块 + 一个类别枚举；删除 tracing 中的循环实现；补一个"gate 缺失即报错"的防御。

### C3. 证据 "found" = provenance 匹配，不等于内容保存

- **位置**：`tracing/lifecycle.py:85-88`（provenance 优先）、`tracing/engine_trace.py`（artifact 收集）。
- **观察**：匹配第一步：任何与 gold 证据共享 `source_turn_id` 的 artifact 即计为该证据"在该阶段存活"，**不管抽取出来的是什么**。例如 "I am a fan of hiking" 会被 `analyzer.py:123` 的 `I am a <occupation>` 模式抽成 occupation="fan of hiking"——同 turn 的垃圾抽取会让 Formation recall 计 1.0。另外 `storage = raw + formation` 恒 ≥ formation，`active_facts(include_history=True)` 连被取代的旧事实都算 found。
- **后果**：RQ2"证据保存率"实际测的是"同 turn 有无 artifact"，不是"信息是否存活"。Formation/Storage recall 会被系统性高估；F1 可能被漏报。
- **建议**：语义阶段（formation/evolution/retrieval/rerank/context）的匹配增加内容校验（精确文本或 ≥ 阈值的语义相似），把纯 provenance 匹配单列为 `match_type=provenance_only` 并分开报告；storage 阶段区分 raw 保存与 semantic 保存。

### C4. F3（Evolution）在构造上不可测

- **位置**：`run_oracle_experiments.py:174`：`evolution = formation`——同一个列表。
- **观察**：trace 没有任何演化操作（更新、冲突、supersede）被施加或测量，evolution recall 恒等于 formation recall，F3 永远不会触发。engine 里有 `governance.py` 和 `valid_from/valid_to/supersedes_id`，但 tracing 层没用。
- **后果**：README 报告 "Evolution recall 1.00" 是测量伪影，不是发现；论文若列出 F3=0% 失败率会是不可辩护的。
- **建议**：要么设计一个受控演化场景（如同一 slot 的事实更新后检查检索到的是否为当前版本，旧版本计 F3），要么在分类法中明确标注"F3 当前未测量"并从指标表中移除该阶段。

### C5. Judge 的前置确定性"自动纠正"通道过宽且未文档化

- **位置**：`evaluation/answer_semantic_eval.py:103-119, 136-149`（`_deterministic_support` 在 LLM judge 之前短路返回）。
- **观察**：候选答案与**任意一条证据**共享 ≥2 个有意义 token 的连续片段，即直接返回 `correct=True, evidence_sufficient=True, confidence=high`——judge 完全不运行，**问题本身也不参与判断**。例：问题问"Where did I volunteer?"，模型答 "adoption agencies"，只要某条证据含 "adoption agencies" 即自动判对。README 97-102 行只文档化了"judge 判错后的窄 lexical-anchor 修复"，这个前置宽通道没有写。
- **后果**：虚高语义正确率，同时压低 F6 candidate 和 E0 案例（它顺带把 evidence_sufficient 也设 True）。`tests/test_evidence_semantic_gate.py` 的第二个用例正好示范了这种宽度。
- **建议**：把确定性通道限制到 README 已文档化的窄规则（judge 之后、证据已判充分、非低置信度时才修复）；或至少要求 anchor 覆盖候选答案全部 token 且与问题有实体级关联。

### C6. Oracle Memory 与 Oracle Context 使用完全相同的答案上下文

- **位置**：`run_oracle_experiments.py:317-318`：两个 mode 都调用 `_score_mode_answer(question, answer, oracle)`——同一份 `oracle` 列表。
- **观察**：两种条件的答案生成输入逐字节相同，因此校准日志里 "Oracle Memory 10/10 vs Oracle Context 9/10" 的差异只能是评测噪声（或历史版本残留），不是条件效应；同时还浪费一倍的 LLM 调用。相关地，"Real Memory > Oracle Context" 倒挂可能部分是上下文形态伪影：real 上下文是 10 个排序混合 artifact，oracle 上下文是全部 gold 证据（可能更长、格式不同），7B 模型对上下文长度/位置敏感。
- **建议**：要么真正区分两条件（Oracle Memory = gold 证据注入记忆存储、经真实检索管线取出；Oracle Context = gold 证据直接放入 prompt），要么合并为一个条件并明说；解释倒挂前先控制上下文条数与格式一致。

## 4. Important 级问题（影响解释，不致命）

### I1. 核心比较缺少配对统计

三条件是按问题配对的，但 `analyze_oracle_results.py` 只报各 mode 独立的 bootstrap CI（48-64 行）——两条不重叠的 CI 不等于配对差异显著。n=10-50 下正确工具是 McNemar/精确二项（基于不一致对）和配对 bootstrap（Real−Oracle 差值）。另：0.30-0.80 的 F1 阈值 sweep（143-151 行）是事后多比较，若之后从 sweep 里选阈值即指标过拟合；协议已冻结 0.5 是对的，sweep 只能作探索性呈现。

### I2. Judge 是单一未验证模型，无可靠性测量

judge 与答案模型同为本地 `qwen2.5:7b`（`answer_semantic_eval.py:19` 默认继承 `ANSWER_MODEL`），无重复采样、无第二 judge、无人工裁定样本。而他们自己的人工抽查 4 例就发现 2 个 judge 假阴性（50%！）——这正是必须量化 judge 可靠性的理由。建议：分层抽样 ~30 例做人工裁定，估计 judge 的精确率/召回率；对 judge 跑 k 次（temperature>0）测自一致性；报告中报告 judge agreement。

### I3. 校准层丢弃证据元数据，两个 gate 证据视图不一致

`semantic_calibration.py:35-43`（`judge_context`）只传 `{id, content}`，丢掉 source/turn/timestamp——而 judge prompt 明说"Timestamps may resolve relative temporal expressions"。主跑的 gate 传全元数据。同一份证据两个视图 → E0 判定可能不一致。统一传全量元数据。

### I4. comparison.jsonl 未存基准参考答案

`run_record`（342-346 行）用 `record["answer"]` 评分但 row 里没有它；`analyze_oracle_results.py:89` 因此永远打印 "(not stored)"。他们整个校准工作流依赖人工逐例检查，却没有把参考答案写进 trace。补 `gold_answer` 字段。

### I5. 论文artifact 级别的可复现性缺口

- 无 LICENSE、无 .gitignore（runner 往 `data/` 写每记录的 SQLite：`run_oracle_experiments.py:87-89`，uuid 命名、永不清理，会被误提交）；
- `requirements.txt` 无 pytest（测试无法从干净 checkout 跑起来）、无 pyarrow（manifest 声明 beam_100k "ready" 但 `_iter_parquet` 需要 pyarrow）、混入 AML 服务依赖（fastapi/uvicorn/psycopg）；
- Ollama 模型 tag `qwen2.5:7b` 是可变 tag，未固定 digest；输出未记录种子与模型版本；
- `results/` 未提交，外部无法检查 n=10 gate 跑的实际产物；
- 根目录 ~25MB 基准数据（longmemeval_oracle.json 15MB 等）+ 自记的 license 待办。

### I6. F1a 诊断混入"抽取器覆盖率"混淆

Formation 是 ~30 条正则的确定性抽取器（`analyzer.py:104-158`），F1a_EXTRACTOR_MISS 很大程度上测的是模式覆盖率而非记忆能力。他们纠正过语言混淆一次（Phase 5），建议把同样的纪律推广到每个 F1 论断。另：`adapters.py:192-193` 的 `by_text` 文本回退会把重复文本静默绑到任意一个同文 turn——正是他们在匹配器里修掉的同类隐患；建议文本回退标记为 `granularity="text_fallback"` 单独计数。

## 7. 总体判断

框架和纪律是这个仓库真正的资产：问题定义、oracle 控制、E0 gate、校准闭环都站在方法论正确的一边，且研究日志的自我纠错记录本身就是论文可信度的证据。当前的瓶颈不在研究想法，而在**仪器（归因代码）没有完全实现协议（文档）**，以及三个测量有效性问题（C3/C4/C5）。Critical 六项都是局部代码修改 + 测试，工作量以天计，远小于带着 instrument bug 跑完 n=50 再返工的代价。修完之后，这个工作的核心主张——"证据全链路到达仍可能答错，oracle 控制可分离记忆侧丢失与下游失败"——在 n=50 + 配对统计 + judge 可靠性报告之下是立得住的。
